# HW2：构建能够修改并复查图表的本地 Agent

## 1. 实验目标

本次作业沿用 HW1 的 Ollama 与 Python 环境，在 `starters/hw02` 中实现一个能够读取、修改和复查 Draw.io 图表的本地 Agent。

实验的重点是让模型通过工具调用提出修改请求，由 Agent 程序负责参数检查、工具分发和文件修改，并通过读取、检查和比较结果确认实际变化。模型的最终回答需要与文件中的真实状态一致，不能仅凭模型声称完成就判断任务成功。

本次实验使用本地 Ollama 模型 `qwen3:4b-q4_K_M`，通过 Python 实现工具层、Agent 控制循环、响应注入测试和 MCP 客户端/服务器调用。

## 2. 工具实现与直接验证

### 2.1 四种工具

在 `starters/hw02/tools.py` 中实现了四种工具：

| 工具 | 功能 |
|---|---|
| `read_diagram` | 读取 Draw.io 页面、图元、连接关系和文件版本 |
| `inspect_diagram` | 检查节点名称及连接端点引用，报告图表问题 |
| `apply_changes` | 执行节点改名、新增连接和调整连接端点 |
| `compare_changes` | 根据前后快照标识比较页面和图元变化 |

四种工具统一采用 `ok`、`data`、`error` 三个字段返回结果。成功时通过 `data` 返回实际数据，失败时通过 `error` 说明原因。

程序对工具输入进行了校验，包括未知参数、参数类型错误、不存在的图元 ID、重复连接 ID、空操作以及超出限制的操作数量。对于批量修改，程序先校验全部操作，只有全部合法时才写入文件，避免部分操作成功、部分操作失败造成文件状态不一致。

每次读取或修改后，程序都会保存快照并分配短标识，同时记录对应文件版本。`compare_changes` 根据模型提供的 `before` 和 `after` 标识获取程序保存的快照，再调用比较逻辑。模型不需要直接管理完整图表数据。

### 2.2 文件安全与版本控制

文件读写由 `diagram_io.py` 提供基础支持。本次实现将操作范围限制在本地实验工作区，并对文件路径、文件大小、编码和 XML 结构进行检查。

修改过程使用内存副本执行，并在写入前再次检查文件版本；写入采用原子替换方式。旧版本写入会被拒绝，避免旧快照覆盖更新后的文件。

### 2.3 直接调用验证

通过直接调用工具函数，对合法修改、未知节点、重复连接 ID、重复改成同一名称、空操作和旧版本写入等情况进行了验证。

验证结果表明，工具能够区分合法请求与无效请求；批量修改在校验失败时不会写入文件，旧版本写入也不会覆盖新版本。

## 3. Agent 控制循环与执行记录

在 `starters/hw02/agent.py` 中实现 `run_agent(request, model)`，负责组织用户请求、调用模型、处理工具调用并返回最终结果。

Agent 的主要执行过程如下：

1. 准备用户消息和工具描述，并请求模型生成响应。
2. 保存原始 assistant 消息。
3. 按顺序处理本轮模型提出的工具调用。
4. 将每次工具执行结果作为 tool 消息返回给模型。
5. 根据模型后续响应继续执行，或结束本次请求。

程序设置了最多 8 轮模型调用和最多 12 次工具调用尝试的限制，第 13 次工具调用不会执行。模型服务失败时结束本次请求；对于未知工具和无效参数等可恢复错误，Agent 会将错误结果返回给模型，以便模型修正请求。无法确定修改对象时，Agent 会向用户询问。

每次请求都会记录执行事件，包括序号、事件类型、工具名、参数、执行结果和相关版本。最终结果包含 `answer`、`stop_reason` 和 `events`，可以根据事件记录还原请求经过模型、工具和文件的过程。

对于修改任务，Agent 需要取得修改后的检查或比较结果，才能向用户说明任务完成。只询问概念的问题则可以直接回答，不需要调用图表工具。

## 4. 六个真实模型任务

本次使用课程提供的 `agent-cases.json` 完成六个真实模型案例。实验使用本地模型 `qwen3:4b-q4_K_M`，并结合工具执行记录和文件实际状态判断结果。

| 案例 | 测试内容 | 实际结果 |
|---|---|---|
| A1 | 直接回答概念问题 | 通过。模型直接回答，没有调用图表工具 |
| A2 | 根据图表内容回答问题 | 通过。Agent 读取 `practice.drawio`，根据实际图表内容回答 |
| A3 | 修改图表中的指定节点 | 部分通过。节点修改成功，但 Agent 没有自动完成后续 inspect/compare 验证，最终达到轮数上限 |
| A4 | 修改节点并增加连接 | 通过。节点改名和新增连接均成功，随后完成检查与比较 |
| A5 | 修改对象不明确的请求 | 通过。Agent 识别到目标不明确并请求用户澄清，没有擅自修改文件 |
| A6 | 读取不存在的文件 | 修复后通过。工具返回读取错误，Agent 将其识别为工具执行失败并结束请求 |

### 4.1 A3：修改成功但自动复查未完成

A3 中，Agent 对节点的修改实际执行成功，但第一次运行没有自动完成后续检查或比较步骤，最终达到轮数上限。

之后通过独立的读取和检查操作确认，目标节点已经发生修改，且 `inspect_diagram` 返回的问题数量为 0。

因此，A3 的文件修改结果是成功的，但 Agent 的完整执行流程没有满足修改后自动复查的要求。本案例记录为部分通过，而不是完整通过。它也说明了工具修改成功与 Agent 完整完成任务是两个不同的判断标准。

### 4.2 A4：修改并复查图表

A4 在 `practice.drawio` 的 `page-a` 页面上执行了两项修改：

- 将节点 `n2` 的名称从“审核申请”修改为“复核”。
- 新增连接 `e-return`，连接方向为 `n3` 到 `n2`。

修改后，Agent 通过检查和比较工具验证结果。`inspect_diagram` 返回 `issue_count=0`，`compare_changes` 显示两项实际变化。

本次修改后的文件版本为：

`f3aa68682bb203e54d3a210a071af6f78c86a503712feb88b3d9eaa64e4b2d06`

该案例验证了 Agent 可以根据模型提出的多个操作修改图表，并通过复查结果确认实际变化。

### 4.3 A5：模糊请求的处理

A5 的请求没有明确指出需要修改哪个步骤。Agent 没有自行猜测目标，而是向用户请求进一步说明，没有对文件执行修改。

该案例验证了 Agent 在修改对象不明确时能够停止修改并请求澄清。

### 4.4 A6：工具错误处理

A6 使用不存在的 `missing.drawio` 进行读取测试。工具返回 `read_error`，Agent 根据错误结果结束本次请求，最终停止原因记录为 `tool_error`。

第一次运行中，错误分类存在问题。调整错误处理逻辑后，未知工具和无效参数等可恢复错误与实际工具执行失败被区分处理，A6 重新测试通过。

## 6. 响应注入测试

在 `starters/hw02/replay.py` 中实现了预设模型响应测试，用于稳定验证 Agent 的控制流程和错误处理逻辑，减少真实模型输出随机性对程序测试的影响。

首先运行基础自测：

```powershell
.venv\Scripts\python.exe starters/hw02/replay.py --self-test
```

基础测试覆盖以下七种情况：

| 测试 | 验证内容 | 结果 |
|---|---|---|
| normal_answer | 模型直接回答 | 通过 |
| unknown_tool | 未知工具处理 | 通过 |
| invalid_arguments | 无效参数处理 | 通过 |
| service_error | 模型服务错误处理 | 通过 |
| loop_limit | 模型轮数上限 | 通过 |
| multiple_tools | 一轮中的多个工具调用 | 通过 |
| tool_call_limit | 工具调用数量上限 | 通过 |

此外，自己构造了三个注入测试：

| 测试 | 验证内容 | 结果 |
|---|---|---|
| tool_exception | 工具执行过程中发生异常时，是否能转换为标准错误结果 | 通过 |
| duplicate_write | 同一批次对同一节点重复写入时的处理结果 | 通过 |
| version_conflict | 使用旧版本进行写入时是否拒绝覆盖新文件 | 通过 |

三个额外测试均通过。`tool_exception` 验证异常能够被捕获并转换为标准错误结构；`duplicate_write` 验证同一批次重复操作的实际结果；`version_conflict` 验证旧版本写入会被拒绝，文件保留更新后的状态。

基础测试 7 项和额外注入测试 3 项合计 **10/10 通过**。

## 7. MCP 调用验证

在 `starters/hw02/mcp_server.py` 中使用 FastMCP 注册 `read_diagram` 和 `inspect_diagram` 两个工具，并通过 stdio 方式启动服务器。

在 `starters/hw02/mcp_client.py` 中实现客户端连接流程，包括：

1. 启动 MCP 服务器并建立 stdio 连接。
2. 初始化客户端会话。
3. 发现服务器提供的工具。
4. 通过 MCP 调用 `read_diagram` 和 `inspect_diagram`。
5. 在进程内直接调用相同工具。
6. 比较两种调用方式返回的业务数据。

比较时去除了每次调用都会变化的 `snapshot_id`，避免将快照标识差异误判为业务结果不一致。

实际测试中，客户端成功完成初始化和工具发现，并调用读取与检查工具。MCP 返回结果与进程内直接调用结果一致，对比测试通过。

另外检查了 `mcp_server.py` 的源码，没有发现使用 `print()` 或其他调试输出写入标准输出的语句。服务器通过 `server.run(transport="stdio")` 启动，标准输出保留给 MCP 协议通信。

## 8. 实验结论

本次作业完成了图表工具、Agent 控制循环、事件记录、响应注入测试和 MCP 调用流程。

工具层实现了统一返回结构、参数校验、快照管理、批量修改校验和文件版本控制。Agent 能够处理多个工具调用、识别部分工具错误、限制模型调用轮数和工具调用次数，并在修改后通过检查或比较结果确认文件状态。

六个真实模型案例中，A1、A2、A4、A5 和修复后的 A6 达到预期结果；A3 的节点修改成功，但自动复查没有完成，因此记录为部分通过。HW1 图表补充测试成功，响应注入测试 10/10 通过，MCP 客户端与直接工具调用结果一致。

实验也体现出模型提出工具调用与程序确认任务完成之间的区别：模型可以决定调用什么工具，但参数合法性、文件修改、版本安全和最终验证必须由程序负责。只有实际文件变化与复查结果能够支持最终结论时，Agent 才应向用户报告任务完成。
